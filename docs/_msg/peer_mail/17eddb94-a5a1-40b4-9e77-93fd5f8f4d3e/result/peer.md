## 1. 조각 나누기 — streamPiecesGrowing (tts.ts:610-635)
- 문장 나누기: 문장부호(. ! ? … 。！？) 뒤 공백이나 줄바꿈에서(SENTENCE_BREAK, tts.ts:58). 문장 안에서는 자르지 않습니다(첫 조각의 쉼표 하나만 예외).
- 빠르기: r = max(1.5, min(빠르기, 3)) (tts.ts:612). 1배여도 1.5로 계획하므로 0으로 나누는 일이 없고, 들으며 1.5배까지 올려도 안전합니다(tts.ts:601 주석). 위는 3배에서 자릅니다.
- 첫 조각(tts.ts:616-624): 첫 문장입니다. 45자(STREAM_FIRST_MAX_CHARS, tts.ts:605)가 넘으면, 앞부분이 8자(STREAM_FIRST_MIN_CHARS, tts.ts:604) 이상 된 첫 쉼표(, ， 、) 뒤에서 자르고 나머지는 다음 조각 앞으로 보냅니다. 첫 문장이 8자보다 짧으면 다음 문장들을 45자 안쪽까지 붙입니다. ⚠ 615줄 주석의 "60자·20자"는 옛 값이고, 코드는 45·8입니다.
- 뒤 조각(tts.ts:628-633): 남은 문장을 차례로 마지막 조각에 붙입니다. 붙일 수 있는 상한은
  limit = min(300, floor((첫 조각 글자 + (지금까지 합 − 마지막 조각 글자) / (r − 1)) × 0.85))
  입니다. 마지막 조각이 두 번째 이상이고 붙여도 limit 이하면 붙이고, 아니면 새 조각을 엽니다. 그래서 두 번째 조각은 늘 새 문장으로 시작합니다.
  예) 1.5배, 첫 조각 40자 → 두 번째 조각 ≤ 102자 → 세 번째 ≤ 275자 → 그 뒤는 300자.
  한 문장이 limit 보다 길면 그 문장 통째로 한 조각이 됩니다(300자가 넘는 문장도 자르지 않습니다).
- 상한: 한 조각 300자(STREAM_PIECE_MAX_CHARS, tts.ts:595). 읽을 글을 지시 칸 한 번(instructions.append, 500토큰)에 넣는 여유입니다(tts.ts:593-594).
- 문단 경계: 넘지 않습니다. 문단 하나 = openSpeechStream 한 번(tts.ts:654, 673)이고, 화면이 문단마다 부릅니다(thinkingPlayer.ts:971).
- 동시에: 문단 안 조각마다 라이브 연결 하나, 최대 8개를 같이 엽니다(LIVE_PARALLEL, tts.ts:55 · streamProduce, tts.ts:570-585). 화면이 앞으로 두 문단까지 미리 열어 최대 세 문단이 겹칩니다(tts.ts:55 주석).

## 2. 시작 전 모음 — 받는 대로 틀기가 전제입니다
- streamStartSec(tts.ts:637-641): r = max(1, 실제 빠르기)(여기는 1.5로 올리지 않습니다). 원본(1배) 소리 초로
  max(1, 첫 조각 글자 ÷ 6.5 × (1 − 1/r) + 0.4)를 소수 둘째 자리에서 반올림합니다.
  6.5 = 노을 말 속도의 낮은 쪽(tts.ts:606) · 0.4 = 조각 끝 판정 동안 다음을 못 내보내는 여유(tts.ts:607) · 최소 1초 = 0.4초만 모으면 첫 문단에서 한 번 끊겨 넣었습니다(tts.ts:608, 639).
- 뜻(tts.ts:600, 636): 첫 조각이 다 만들어지기 전에 r배로 다 들어 버리지 않을 만큼만 모으고 틉니다. 서버는 받은 소리를 0.3초씩 바로 내보내고(STREAM_CONT_CHUNK_MS, tts.ts:609 · streamDrain, tts.ts:535-540), 화면은 원본이 startSec 만큼 모이면 틀기 시작해 하나의 시계에 이어 붙입니다.
- 한 프로세스라면(제 의견): 서버 작업(StreamJob)의 모양을 그대로 쓰시면 됩니다.
  · 조각마다 {받은 PCM 블록 목록, done} 하나씩, 그리고 지금 트는 조각 번호(cursor)를 둡니다.
  · 만드는 쪽은 노을이 소리를 보낼 때마다 그 조각 목록에 붙이고(tts.ts:575-578, sink 콜백), 끝나면 done 을 켭니다(tts.ts:581).
  · 트는 쪽은 cursor 조각에서 블록을 꺼냅니다. 그 조각이 done 이고 다 꺼냈으면 cursor+1 로 넘어갑니다(tts.ts:527-533). 비었는데 done 이 아니면 기다리고, 그때가 끊김입니다. 처음엔 cursor 0 에 모인 원본이 startSec 를 넘을 때 시작합니다.
  · read_noeul 이 "끝까지 읽힌 뒤 PCM 을 돌려주는" 모양이면 받는 대로 넘기는 콜백이 필요합니다 — 우리 requestOpenaiAudio/liveRead 의 sink 인자가 그 역할입니다(tts.ts:298, 329).

## 3. "조각이 다 되면 넘김" 비교 — 실측 기록에는 없습니다
- stream_sim2.cjs 는 받는 대로 틀기만 흉내 냅니다(머리 주석 2-6줄: startSec 모은 뒤 원본을 r배로 써 나가며 바닥나면 끊김으로 셈, 다음 두 문단 미리 맡김).
  · stream_sim2_r15.log(최소 1초 넣기 전): 1·1.1·1.3배 각 1번 끊김(문단1 안 150~580ms), 1.5배 0번.
  · 넣은 뒤 _b·_c·_d.log: 1~1.5배 모두 끊김 0번, 첫 소리 3.4~5.8초.
- 계산으로 본 차이(실측 아님):
  · 첫 소리: 첫 조각을 노을이 다 말할 때까지 기다리므로 첫 조각(최대 45자)이면 약 7초 + 연결 시간으로 늦어집니다.
  · 뒤 조각 조건: 받는 대로 틀기는 L_k ≤ L_0 + 앞합/(r−1) 이지만, 다 되면 넘김은 앞 조각들을 다 들은 시점에 다 만들어져 있어야 해서 L_k ≤ L_0 + 앞합/r 로 더 빡빡합니다. 우리 식을 그대로 쓰면 1.5배에서 두 번째 조각(최대 L_0 × 2.55)이 상한(L_0 × 1.67)을 넘어 끊깁니다. 1배도 마찬가지(상한 2 × L_0)입니다.
  · 그래서 이 방식으로 가신다면 limit 식의 (r − 1)을 r 로 바꾸고, 조각 끝 판정 시간(끝 판정 1.5/0.3초)만큼 여유를 더 두셔야 합니다. 조각이 작아져 연결 수가 늘어나는 것도 함께 보셔야 합니다. 직접 재 보시길 권합니다.

## 4. 읽는 도중 빠르기가 바뀔 때 — 계획을 다시 하지 않습니다
- 문단을 열 때의 빠르기로 한 번 계획합니다(thinkingPlayer.ts:971 rate: this.rate → tts.ts:672-673). 재생 빠르기만 바로 바뀝니다(setRate).
- 조각 계획은 1.5배로 잡아 두어 들으며 1.5배까지 올려도 됩니다(tts.ts:601, 612). 그보다 더 올리면 지금 문단과 미리 연 두 문단은 그 계획 그대로라 끊길 수 있고, 그다음 여는 문단부터 새 빠르기로 계획합니다. startSec 도 열 때의 실제 빠르기로 계산합니다(tts.ts:638).

## 5. 문단 이동·멈춤 때 열어 둔 연결 정리
- 문단 이동: 화면이 지금 문단보다 앞이거나, 미리 열 범위(두 문단) 밖의 슬롯을 버립니다(thinkingPlayer.ts:948 dropSlot). 슬롯을 버리면 취소 요청(cancelStream)을 보냅니다(thinkingPlayer.ts:104-121).
  → 서버는 작업 상태를 끝내고 controller.abort() 한 뒤 기다리던 요청을 깨우고 작업을 지웁니다(streamCancel, tts.ts:555-560 · cancelSpeechStream, tts.ts:708-712).
  → abort 를 받은 라이브 연결마다 session.close 를 보내고 3초 뒤 웹소켓을 닫습니다(tts.ts:362-366).
- 끝내기: 모든 슬롯을 버립니다(thinkingPlayer.ts:797).
- 멈춤: 연결을 끊지 않습니다. 재생만 멈추고(thinkingPlayer.ts:814-818), 열린 연결은 그 조각을 끝까지 만들고 화면은 계속 받아 둡니다.
- 안전망: 화면이 120초 동안 묻지 않은 작업은 서버가 정리합니다(STREAM_IDLE_MS, tts.ts:39 · tts.ts:561-563). 동시 작업이 12개를 넘으면 오래된 것부터 정리합니다(tts.ts:40, 564-567). 문단 전체에는 시간 제한이 있습니다(liveTimeoutMs, tts.ts:682). 한 조각이 실패하면 나머지도 abort 합니다(tts.ts:580).

## 6. 노을 사용량
- 들어갑니다. Paseo 는 %APPDATA%\BluemingReadAloud\tts-usage.json 의 months[달]을 chirp3hd·wavenet·openai 셋으로 "PC 읽기 앱" 몫에 더합니다(readReadAloudUsage, tts.ts:1380-1386 · monthCounts, tts.ts:1374-1377). 달은 Google 결제 달(태평양 시간, billingMonth)입니다 — 앱도 같은 달 계산을 쓰시는지 확인해 주십시오.
- 키 칸은 그렇게 두시면 됩니다: keys[usageKeyMark(OpenAI 키).id] = { tail, months: { 달: { openai: n } } }.
  · id 는 키를 trim 한 뒤 sha256 hex 앞 12글자, tail 은 trim 뒤 끝 4글자입니다(tts.ts:1083-1086).
  · Paseo 자신의 OpenAI 키 칸과 같은 id 로 합쳐집니다(addKeyed, tts.ts:1197-1204 · 합계 파일, tts.ts:1465-1475).
- ⚠ 파일에 keys 가 있으면 Paseo 의 키별 합은 keys 만 보고 months 는 보지 않습니다(keyedMonthCounts, tts.ts:1176-1195). 그래서 months 와 keys 두 곳에 같은 숫자를 올려 주셔야 합니다. Paseo 의 countUsage 도 두 곳에 같이 더합니다(tts.ts:1140-1160). 파일에 v 칸이 있으면 1이어야 읽습니다(tts.ts:1185).
- 세는 법: 노을 연결(조각) 하나가 성공할 때마다 그 조각 글의 글자 수(코드 포인트)를 셉니다(tts.ts:371, 1141). 다시 시도로 버린 연결과 실패한 연결은 세지 않습니다(finish 의 실패 경로가 371줄 전에 끝남). 실제 OpenAI 요금은 소리 초 단위이고 글자 수는 우리 셈법입니다(tts.ts:371 주석).
- ⚠ 두 번 세기 주의: 크롬 확장용 창구(/v1/tts/noeul)로 읽은 것은 확장이 자기 기록에 셉니다(크롬 확장 대화가 이쪽에 알린 6d6daf7d). 앱 파일에는 앱이 직접 읽은 것만 넣으셔야 합니다.
- "PC 읽기 앱" 몫은 설정 화면 "이번 달 Paseo"에서는 빠집니다(tts.ts:1420, 1475).
