## 2. 사용자 관측 증상에 대한 설명

**Aside: 화면 밖에서 돌아와도, 다음 조각에서도 안 보임.** 정상적인 화면 밖 범위라면 주기적 재조회(`REFRESH_S=1.0`)와 새 조각의 `_select()` 때문에 돌아온 뒤 다시 그려진다. 가짜 UIA에서도 그렇게 됐다. 반대로 보관한 범위들이 스크롤 뒤 계속 빈 결과를 반환하면 `_raw_rects=[]` → `_redraw()`가 숨김 → 1초 뒤 같은 빈 결과가 반복된다. 다음 조각도 같은 영향을 받으면 읽기 끝까지 안 보인다. 빈 결과는 `lost` 예외가 아니므로 `_stop` 기록이 없고, `active` 및 whisperer의 `"on"` 상태가 유지돼 리더 창도 뜨지 않는다.

이 경로는 **사용자 관측 전체와 일치하지만, 실제 Aside 실행에서 범위가 빈 결과를 반복했는지는 당시 로그로 입증되지 않는다.** 마지막 숨김 직후의 사각형 수·문서 경계·전경 상태·조각 번호가 기록되지 않았다. 다음 조각이 애초에 `_mapped`에 없었던 경우, 전경 판정이 계속 거짓이었던 경우, 문서 경계에 계속 잘린 경우도 로그만으로 배제할 수 없다.

**VS Code: 위쪽의 좁고 작은 번역문 막.** `_redraw`는 받은 사각형을 `clip_rects`로 문서·창 경계에 자른 뒤 번역문 막에 넘긴다. `build_caption_bitmap`은 **잘린 사각형의 폭**으로 줄바꿈하고 **잘린 높이의 가운데 값**으로 글꼴을 맞춘다. 예컨대 `(100,200,500,230)`이 경계 때문에 `(300,215,500,225)`가 되면 입력 폭은 400→200px, 높이는 30→10px이다. 따라서 좁은 막과 작은 글씨는 코드상 설명된다.

다만 `clip_rects`는 위쪽 좌표를 더 위로 옮기지 못한다(`top=max(raw_top,bound_top)`). 번역문 막은 계산된 위쪽에서 테두리·여백 **4px**만 더 올린다. **원문보다 크게 위에 나온 위치 자체는 UIA가 이미 위쪽의 잘못된 사각형을 주었거나, 원문의 실제 화면 위치가 사각형 조회 뒤 움직였어야** 설명된다. 어느 쪽인지는 VS Code 로그에 좌표가 없어 확정할 수 없다.

## 3. 네가 보는 근본 원인

가장 설명력이 높은 공통 고리는 **읽기 시작 때 검증한 UIA 조각 범위를 이후에도 같은 글의 범위라고 가정하는 것**이다. Chromium은 접근성 하위 트리 삭제 시 끝점을 다른 유효 위치로 조정할 수 있다. 스크롤 중 가상 목록이나 동적 문서가 트리를 바꾸면, 보관한 여러 조각 범위가 예외 없이 빈 사각형 또는 엉뚱한 사각형을 반환할 수 있다. 현재 앱은 이를 내용으로 확인하지 않고, 빈 결과는 계속 숨기며, 잘못된 결과는 그대로 그린다. VS Code의 채팅 패널에는 특히 그 가능성이 있다. Aside에서 읽은 사이트와 실제 접근성 트리 변경 여부는 미확인이다.

별도로 **번역문 막의 글꼴·폭을 화면에 남은 잘린 조각으로 다시 계산하는 것**은 확인된 크기 증폭 결함이다. 범위가 올바르더라도 문단이 일부만 보이면 글꼴이 작아질 수 있다. 이 결함만으로 큰 위쪽 위치 오차나 끝까지 사라지는 현상은 설명되지 않는다.

## 4. Claude 가설에 대한 판정

- **H1 부분 채택.** “범위가 한꺼번에 죽는다”보다 **끝점이 조정돼 다른 위치를 가리키거나 빈 결과를 계속 준다**가 정확한 후보다. Chromium 원본이 예외 없는 끝점 조정 경로를 뒷받침한다. 실제 Aside 사건의 발생 여부는 아직 미계측이다.
- **H2 낮음.** `_rects`의 정상·예외 경로는 결과를 보내고, 현재 세대의 `rects` 결과는 `_inflight`를 해제한다. 가짜 재현에서는 계속 조회하면서도 보이지 않았고 `_inflight=False`였다. 워커 정지나 Tk 틱 중단을 당시 로그만으로 완전히 배제할 수는 없다.
- **H3 부분 채택.** 자른 높이로 글꼴을 정하는 문제는 확실하다. 스크롤 애니메이션 중 받은 낡은 좌표도 가능한 원인이다. 그러나 `clip_rects`만으로 원문보다 크게 위쪽의 위치는 만들 수 없다.

## 5. 수정 방법 (before → after) · 대안 비교와 추천 · 함정

### 권장 순서

**1. 범위의 글을 제한된 길이로 재검증하고, 틀리면 그 사각형을 그리지 않기.**

현재 `_rects`는 다음과 같다.

```python
arr = call("GetBoundingRectangles", r.GetBoundingRectangles)
rects = rects_from_uia(arr)
```

`begin` 때 각 조각 범위에서 확인한 UIA 글을 워커 세션에 보관하고, 이후 위치 조회에서는 해당 **조각 범위의 짧고 길이 제한된** `GetText(max_count)`로 대조한다. 불일치하거나 범위가 접혔으면 `range_changed`로 처리한다. 긴 조각은 앞·뒤의 제한된 구간을 각각 검사한다. **스크롤 뒤의 범위에 `GetText(-1)`을 호출하면 안 된다.** 범위가 문서 쪽으로 옮겨졌을 가능성 때문에 사실상 금지된 문서 전체 조회가 될 수 있다.

```python
# 개념 코드: 모든 UIA 호출은 _UiaWorker에서 _call로 감싼다.
expected = s.expected_text[idx]       # begin 때 검증한 조각의 UIA 글
if not bounded_range_text_matches(call, r, expected):
    raise _Lost("range_changed")
arr = call("GetBoundingRectangles", r.GetBoundingRectangles)
```

검증 함수에는 호출당 상한, 호출 시간 1초 제한, 긴 조각의 양끝 검사와 유니코드 길이 처리가 필요하다. 글 일치만으로 좌표까지 증명되지는 않으므로, 스크롤 직후 첫 사각형은 **문서 영역과의 교차·기존 줄 크기에서의 급격한 변화**도 검사하고 수상하면 숨긴 채 한 번 더 조회한다. 작은 사각형이라는 이유만으로 영구 폐기하면 실제로 일부만 보이는 문단을 오판할 수 있으므로, 재조회 횟수를 제한하고 실패 시 리더 창으로 넘긴다.

**2. 자동 복구는 현재 선택 범위 안에서 한 번만 시도하고, 실패하면 리더 창으로 넘기기.**

범위 불일치 시 워커에서 현재 포커스 요소의 조상을 제한 깊이로 걷고 `GetSelection`을 다시 얻는다. **새 선택의 글이 처음 선택한 글과 일치할 때만** `align_source_to_uia`와 `_build_ranges`로 모든 조각 범위를 다시 만든다. 선택이 사라졌거나 다르면 전체 문서 검색 없이 복구를 포기한다. 휠마다 재시도하지 말고 정지 후 한 차례와 제한된 재시도만 허용한다.

현재 중단 연결은 콘솔 기록만 한다.

```python
def _on_source_highlight_stop(reason=""):
    log_to_console(f"...{reason}...")
```

복구 실패 뒤에는 기존의 결과 분기를 재사용해 상태를 `"off"`로 바꾸고, 리더 창 설정이 켜져 있으면 현재 조각으로 넘긴다.

```python
def _on_source_highlight_stop(reason=""):
    session = _source_hl_session
    log_to_console(f"...{reason}...")
    if session is not None and session is tts_session:
        _on_source_highlight_result(session, False, reason)
```

같은 글인지 확인할 수 없는 범위를 **그대로 다시 그리는 “다시 표시” 버튼은 문제를 해결하지 못한다.** 버튼을 둔다면 “현재 선택을 다시 잡아 검증 → 실패하면 리더 창 표시”를 수행해야 한다. 선택이 이미 사라진 경우에는 재선택이 필요하다고 안내해야 한다. 새 사용자 문구는 `messages.py`의 `ko`·`en` 양쪽에 넣어야 한다.

**3. 번역문 막 크기를 잘린 높이에서 분리하기.**

현재 흐름은 `raw → clip_rects → build_caption_bitmap`이다. 검증된 원래 줄 높이와 문단 폭을 조각별로 보관해 글꼴과 줄바꿈에 쓰고, **최종 비트맵만** 문서·창 경계로 자르는 쪽을 권장한다. 이때 화면 밖까지 불투명 막이 덮이지 않도록 최종 비트맵을 실제로 잘라야 한다. 원래 치수를 복구할 수 없거나 사각형이 수상하면 작은 번역문 막을 억지로 그리지 말고 숨기거나 리더 창으로 전환한다. 글꼴의 최소값만 올리는 수정은 좁은 폭·잘못된 위치를 남긴다.

### 대안 비교

| 방법 | 효과 | 한계 |
|---|---|---|
| 스크롤 뒤 대기 시간 증가 | 애니메이션 중 좌표 오차 감소 | 바뀐 범위·지속 소실은 해결하지 못함 |
| `GetText` 제한 조회와 현재 선택에서 재획득 | 잘못된 범위 탐지, 선택이 남은 경우 복구 | 선택 소실 시 복구 불가; 호출 길이·시간 제한 필수 |
| 실패 시 리더 창 자동 전환 | 읽기 끝까지 아무 표시도 없는 상태 방지 | 원문 위 표시 자체는 복구하지 못함 |
| 하단 바 “다시 표시” | 사용자가 재시도 가능 | 검증·재획득 없이 `_redraw()`만 부르면 낡은 좌표 재사용 |
| 전체 문서 재검색 | 위치를 찾을 가능성 | 이 PC의 UIA 금지 규칙 위반. 추천하지 않음 |

**추천은 제한된 범위 검증 → 현재 선택으로 한 차례 재획득 → 실패 시 리더 창 전환**이다. 재획득이 불가능한 경우에도 침묵하며 끝까지 숨기는 상태는 없앤다.

### 진단 로그의 사각지대

현재 “보임”은 `overlay.show()` 호출 뒤 기록된다. 그런데 `_Overlay.show()`는 `UpdateLayeredWindow` 실패 시 내부에서 숨기고 그냥 반환하며, 호출자는 그래도 `_overlay_visible=True`로 기록할 수 있다. 성공 여부를 반환하게 해 **실제 표시 성공 후에만** “보임”을 남겨야 한다. 두 사건 로그에는 해당 실패 경고가 없어 이번 원인이라는 증거는 없다.

다음 재현에는 글 내용이나 인증값 없이, 상태가 바뀔 때만 `gen`, 재생 조각 번호, `_mapped` 여부, `_inflight`와 요청 경과 시간, `_fg_ok`, `_scroll_hold`, 원시 사각형·문서 경계·잘린 사각형, 제한 조회의 **일치 여부**, 실제 표시 성공 여부를 남겨야 한다. `whisperer`의 실제 `segment` 이벤트 번호도 남겨 선합성과 재생을 구분해야 한다.

## 7. 확신도와 남은 불확실성

- **높음:** 현재 코드는 begin 뒤 조각 범위의 글을 재검증하지 않는다. 정상 범위라면 화면 복귀 시 다시 표시된다. `clip_rects` 뒤 치수로 번역문 막의 폭·글꼴을 정한다. 빈 UIA 결과는 `_stop` 없이 숨김을 유지할 수 있다.
- **중간:** Chromium의 끝점 조정이 두 증상을 함께 만든다는 설명. Chromium 원본과 가짜 재현은 이를 지지하지만, 실제 Aside·VS Code의 당시 UIA 반환값은 없다.
- **낮음/미확인:** Aside 사이트의 동적 렌더링 여부, 다음 조각의 실제 재생 시각과 `_mapped` 값, VS Code에서 원시 사각형이 위쪽으로 간 정확한 원인, 설치된 두 앱의 Chromium 구현 버전. 이 자료 없이는 H1을 사건의 확정 원인이라고 선언할 수 없다.

## 8. 이 머신에서 접근 불가한 자료

요청서가 열거한 조사 원본은 모두 열었다. 다만 지정 응답 파일과 허용된 `.scratch/`에 대한 쓰기가 모두 **`Access denied`**로 실패했다. 두 경로에 파일이 생성되지 않았음을 확인했다. 따라서 이 전체 응답을 최종 메시지로 제출한다. 실제 앱에 UIA를 호출하지 않았고 프로덕션 파일·Git 상태·설치 상태를 변경하지 않았다.
