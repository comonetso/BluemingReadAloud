### 1-1. 크롬 확장 대신 노을로 읽어 주는 창구 (de72342)
**배경/요구**: Paseo 상태바 대화가 세 읽기 앱의 OpenAI 목소리를 노을 하나로 맞추자고 사전 승인 요청을 보냈다[1]. 그때 이 앱엔 OpenAI 칸 자체가 없어 "바꾼 파일 없음"으로 회신했다. 이어 크롬 확장 대화가 요청했다[3]. 노을은 라이브 웹소켓이라 키를 Authorization 머리글로만 받는데, 브라우저는 웹소켓에 머리글을 못 붙인다. 그래서 이 앱의 127.0.0.1:51888 에 노을 길을 열어 달라는 요청이었다. 덧붙인 조건은 동시 12개, 끊으면 라이브 연결 닫기, Paseo 11-18 판 따르기였다[7].
**처리**: `noeul_live.py` 를 새로 만들었다(표준 라이브러리만 쓴 웹소켓 클라이언트). `tts_usage.py` 창구에 `POST /v1/tts/noeul` 을 더했다. 키는 처음엔 Paseo 키 파일이었다[4] → 1-3 에서 바뀜.
**결과**: 설치본 11-18 15:21 에 확장 요청이 소리 남(76자 → 소리 11.8초, 응답까지 17.5초). 리규형님 "정상".

### 1-6. 크롬 확장 흘려받기 노을 길 (마무리 뒤, 확장 요청 20321079)
**배경/요구**: 마무리(bfaa9c9) 뒤 크롬 확장 대화가 사전 승인된 수정 요청을 보냈다(그쪽 리규형님 버튼 "컨펌 없이 수정"). 그쪽 리규형님 실측으로 확장 노을 첫 소리가 PC 앱보다 3~4배 늦어, 확장도 PC 앱 방식으로 해 달라는 요청이었다. 확장은 문단을 맡기고 오디오 요소로 흘려받아 틀고, 문단 안의 점점 큰 조각·동시·이어 붙이기는 이 앱이 맡는다. 규격 초안과 실측(250KB 모음, crossOrigin, Range)이 함께 왔다.
**처리**: 규칙대로 이쪽 리규형님께 묻지 않고 파일만 고쳤다(고칠 파일에 남의 미커밋 변경 없음, 진행 중 작업 없음).
- `noeul_live.py`: 연결 자리를 순서표 방식(`_Slots`)으로 바꿨다 — 먼저 맡긴 문단의 앞 조각부터 자리를 얻는다. `read_noeul(priority=)`, `ExtensionStreams`(맡기기·흘림·결과·취소·청소), `StreamWidener`(24kHz 한 채널 → 48kHz 두 채널, 사이 값은 앞뒤 평균), `wav_stream_header`(길이 칸 0xFFFFFFFF)를 넣었다.
- `tts_engine.py`: `stream(lang=, group=)` 을 받고, 실패에 code 를 붙인다.
- `tts_usage.py`: 네 길 + OPTIONS 와 Access-Control-Allow-Origin 을 넣었다.
- `whisperer.py`: 창구에 연결했다.
- Claude 가 정한 값: 보관 10분(안 연 작업·끝난 결과) — 확장이 "그쪽이 정해 달라"고 맡겼다. 흘리기 시작은 PC 앱 재생기와 같은 시작 전 모음 뒤.
**결과**: 새 시험 29개, 전체 559개 통과, 노을·창구 시험 다섯 번 되풀이 모두 통과. 확장에 completed 답장(최종 규격·제약·파일). 커밋 ab5d15b(이쪽 리규형님 버튼 "커밋하고 개발 모드로 확인").

## 4. 발견한 코드베이스 함정
- **재생기는 빈 블록을 조각의 끝으로 본다**(tts_engine 재생 고리, Codex 1턴 지적). 받는 대로 틀기에서는 "아직 안 옴"과 "다 됨"을 갈라야 한다 → `GrowingAudio`(빈 읽기 ≠ done).
- **WSOLA 늘이기가 수신 공백에서 flush 하면 소리가 끊긴다** → `_StreamingStretcher` 는 공백에서 flush 하지 않는다.
- **창구가 본문을 다 읽지 않고 거절하면 Windows 가 RST 를 보낸다** — 클라이언트는 403·413 대신 연결 끊김을 본다. `tts_usage._read_body_first` 로 먼저 읽는다.
- **개발 모드와 설치본은 설정 파일이 따로다** — 저장소 `whisperer_settings.json` / `C:\Program Files\BluemingReadAloud\whisperer_settings.json`. 설치본 콘솔 로그는 앱 폴더 바로 아래 `whisperer_console.log`.
- **실행 중인 앱의 설정 파일을 밖에서 고치면 덮인다** — `save_settings()` 가 들고 있던 값으로 파일 전체를 다시 쓴다. 실행 중인 설치본에 키를 넣을 땐 인증 창을 쓴다.
- **줄바꿈**: 작업 사본에서 whisperer.py·tts_engine.py·readaloud_text.py 는 CRLF, 나머지(noeul_live·tts_usage·translation·messages·tests)는 LF. Git Bash 의 `cat -A`·`grep $'\r$'` 는 틀리게 보였다 → 파이썬 바이트로 센다.
- **옛 확장 노을 길은 첫 소리가 늦다** — `POST /v1/tts/noeul` 은 조각 하나를 통째 WAV 로 돌려주고, 확장은 다 받은 뒤에야 튼다(76자 → 17.5초). 그쪽 리규형님이 실측해 PC 앱보다 3~4배 늦다고 보고 흘림 길을 요청했다 → 1-6.
- **크롬은 흘려받는 소리도 약 250KB 를 모은 뒤 튼다**(확장 실측) — 24kHz 한 채널이면 5.2초, 48kHz 두 채널이면 1.3초. 흘림 길이 48kHz 두 채널로 늘려 보내는 까닭.
- **오디오 요소에 127.0.0.1 주소를 그냥 넣으면 크롬이 막는다**(MEDIA_ERR_SRC_NOT_SUPPORTED) — `crossOrigin="anonymous"` + 응답의 Access-Control-Allow-Origin 이 있어야 튼다(확장 실측).
- **시험을 모듈 이름으로 고르면 test_noeul_streaming 이 불러오기 실패** — 그 파일이 같은 폴더의 test_noeul_live 를 불러온다. `python -m unittest discover -s tests -p "test_noeul*.py"` 처럼 폴더 방식으로 돌린다.
- **브라우저 웹페이지(http/https)에서는 이 앱이 쉰다**(Disable in Browsers 기본 켜짐) — 이 앱 실사용 시험은 메모장 등에서 한다.

- stream_sim2.cjs 는 받는 대로 틀기만 흉내 냅니다(머리 주석 2-6줄: startSec 모은 뒤 원본을 r배로 써 나가며 바닥나면 끊김으로 셈, 다음 두 문단 미리 맡김).
  · stream_sim2_r15.log(최소 1초 넣기 전): 1·1.1·1.3배 각 1번 끊김(문단1 안 150~580ms), 1.5배 0번.
  · 넣은 뒤 _b·_c·_d.log: 1~1.5배 모두 끊김 0번, 첫 소리 3.4~5.8초.
- 계산으로 본 차이(실측 아님):
  · 첫 소리: 첫 조각을 노을이 다 말할 때까지 기다리므로 첫 조각(최대 45자)이면 약 7초 + 연결 시간으로 늦어집니다.
  · 뒤 조각 조건: 받는 대로 틀기는 L_k ≤ L_0 + 앞합/(r−1) 이지만, 다 되면 넘김은 앞 조각들을 다 들은 시점에 다 만들어져 있어야 해서 L_k ≤ L_0 + 앞합/r 로 더 빡빡합니다. 우리 식을 그대로 쓰면 1.5배에서 두 번째 조각(최대 L_0 × 2.55)이 상한(L_0 × 1.67)을 넘어 끊깁니다. 1배도 마찬가지(상한 2 × L_0)입니다.
  · 그래서 이 방식으로 가신다면 limit 식의 (r − 1)을 r 로 바꾸고, 조각 끝 판정 시간(끝 판정 1.5/0.3초)만큼 여유를 더 두셔야 합니다. 조각이 작아져 연결 수가 늘어나는 것도 함께 보셔야 합니다. 직접 재 보시길 권합니다.

## 4. 읽는 도중 빠르기가 바뀔 때 — 계획을 다시 하지 않습니다
- 문단을 열 때의 빠르기로 한 번 계획합니다(thinkingPlayer.ts:971 rate: this.rate → tts.ts:672-673). 재생 빠르기만 바로 바뀝니다(setRate).
- 조각 계획은 1.5배로 잡아 두어 들으며 1.5배까지 올려도 됩니다(tts.ts:601, 612). 그보다 더 올리면 지금 문단과 미리 연 두 문단은 그 계획 그대로라 끊길 수 있고, 그다음 여는 문단부터 새 빠르기로 계획합니다. startSec 도 열 때의 실제 빠르기로 계산합니다(tts.ts:638).

## 5. 문단 이동·멈춤 때 열어 둔 연결 정리
- 문단 이동: 화면이 지금 문단보다 앞이거나, 미리 열 범위(두 문단) 밖의 슬롯을 버립니다(thinkingPlayer.ts:948 dropSlot). 슬롯을 버리면 취소 요청(cancelStream)을 보냅니다(thinkingPlayer.ts:104-121).
  → 서버는 작업 상태를 끝내고 controller.abort() 한 뒤 기다리던 요청을 깨우고 작업을 지웁니다(streamCancel, tts.ts:555-560 · cancelSpeechStream, tts.ts:708-712).
  → abort 를 받은 라이브 연결마다 session.close 를 보내고 3초 뒤 웹소켓을 닫습니다(tts.ts:362-366).
- 끝내기: 모든 슬롯을 버립니다(thinkingPlayer.ts:797).
- 멈춤: 연결을 끊지 않습니다. 재생만 멈추고(thinkingPlayer.ts:814-818), 열린 연결은 그 조각을 끝까지 만들고 화면은 계속 받아 둡니다.
- 안전망: 화면이 120초 동안 묻지 않은 작업은 서버가 정리합니다(STREAM_IDLE_MS, tts.ts:39 · tts.ts:561-563). 동시 작업이 12개를 넘으면 오래된 것부터 정리합니다(tts.ts:40, 564-567). 문단 전체에는 시간 제한이 있습니다(liveTimeoutMs, tts.ts:682). 한 조각이 실패하면 나머지도 abort 합니다(tts.ts:580).
